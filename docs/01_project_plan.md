## 0. 이 문서의 용도

이 문서는 프로젝트의 **기준 문서**다. 결정된 사항을 한곳에 모아두어, 작업 중간에 방향을 잃지 않도록 하고, 새로운 작업 세션에서도 이 문서만 보면 맥락을 바로 잡을 수 있도록 한다. 개발이 진행되며 결정이 바뀌면 이 문서를 먼저 업데이트한다.

## 1. 프로젝트 개요

고객센터·민원 부서에는 신청·변경·취소·오류·일반·긴급 등 반복 문의가 계속 접수된다. 담당자가 매번 유형을 판단하고 규정·FAQ를 찾아 답변을 작성하므로 처리 시간이 길고 답변 품질도 담당자마다 다르다.

본 프로젝트는 문의를 AI가 자동 분류하고, RAG로 관련 규정·FAQ·매뉴얼을 검색한 뒤, 담당자가 검토·수정해 사용할 수 있는 답변 초안을 생성하는 웹 시스템을 개발한다.

### 대상 도메인: 전기 회사 민원 (경력인증 유형 강조)

본 시스템은 전기 회사의 **민원 전반**(신청·변경·취소·오류·일반·긴급 등)을 분류·답변하는 시스템이다. 특정 한 가지 업무 전용이 아니다.

다만 실제 의뢰처(전기 관련 사업체)에서 **경력 인증 발급 문의가 많다**는 점을 반영하여, 문의 유형에 "경력인증"을 하나 추가하고 해당 시나리오를 데모에서 비중 있게 다룬다. 경력증명서 발급, 경력 인정 기준, 경력수첩, 제출 서류 등은 규정이 명확해 RAG 근거 문서로도 잘 갖출 수 있다.

> 정리: 경력 인증은 **시스템의 주제가 아니라 여러 문의 유형 중 하나**다. 시스템 전체는 전기 회사 민원 처리이며, 경력 인증은 문의가 많은 만큼 추가·강조되는 유형이다. (멘토링에서 추가된 방향)

## 2. 핵심 기능과 우선순위

기능을 우선순위로 명확히 구분한다. 1인 프로젝트이므로 **위에서부터 순서대로 완성**하며, 각 단계가 끝날 때마다 "여기서 멈춰도 시연 가능한 상태"를 유지한다.

| 순위 | 기능 | 설명 | 비고 |
|---|---|---|---|
| 1 | 분류 → 룰 → RAG 검색 → 답변 생성 | 텍스트 문의를 끝까지 처리하는 핵심 파이프라인 | 평가 점수 65%가 여기 집중 |
| 2 | 도메인 데이터 채우기 (경력인증 유형 포함) | RAG 지식베이스·분류유형·룰·프롬프트를 전기 회사 민원에 맞춤. 경력인증 유형·자료를 추가 | RAG 품질 = 핵심 차별화 |
| 3 | CLOVA OCR | 경력·재직증명서 등 서류 이미지 → 텍스트 | 서류 기반 문의에 유용, 임팩트 큼 |
| 4 | CLOVA Speech (STT) | 통화 녹취 음성 → 텍스트 | 음성 샘플 확보 부담, 마지막 |

**중요 원칙**
- OCR/STT는 기존 파이프라인 **앞에 붙는 입력 변환기**일 뿐, 분류·RAG 로직은 건드리지 않는다.
- 1·2순위(분류·RAG)가 점수의 핵심이다. 여기를 먼저, 확실하게 끝낸다.
- OCR/STT는 안전판 역할도 한다. 일정이 밀리면 4순위(STT)부터 잘라도 핵심 점수는 지켜진다.

## 3. 기술 스택

| 구분 | 기술 | 비고 |
|---|---|---|
| Frontend | React | 문의접수·대시보드·답변편집 화면 |
| Backend | FastAPI (Python) | RAG/LLM 생태계가 Python이라 유리 |
| LLM | GPT API 또는 Claude API | 분류 + 답변 초안 생성 |
| RAG | LangChain | 문서 검색 기반 답변 생성 |
| Vector DB | ChromaDB | FAQ·매뉴얼 임베딩 저장 (로컬 파일) |
| DB | PostgreSQL | 문의·처리이력·사용자·부서 정보 |
| OCR | 네이버 클라우드 CLOVA OCR | 서류 이미지 → 텍스트 |
| STT | 네이버 클라우드 CLOVA Speech | 통화 음성 → 텍스트 |
| 평가 | Accuracy, F1-score, 답변 적합도 | 분류 정확도·답변 품질 |

**구동 환경**: 배포 없이 로컬(localhost)에서 구동·시연한다. 단, OCR/STT/LLM/임베딩은 인터넷 너머의 클라우드 API를 HTTPS로 호출하므로 인터넷 연결과 API 키가 필요하다.

## 4. 시스템 흐름

문의 한 건이 처리되는 순서는 다음과 같다.

1. 문의 접수 — 텍스트 직접 입력, 또는 서류 이미지(OCR)·통화 음성(STT)을 텍스트로 변환
2. LLM 분류 — 유형·핵심요청을 JSON으로 추출
3. 룰 적용 — 우선순위·담당부서 확정
4. RAG 검색 — Vector DB에서 근거 문서 검색
5. 답변 초안 생성 — 검색된 근거를 바탕으로 LLM이 작성
6. 담당자 검토·발송 — 초안 수정 후 최종 답변

아키텍처 구성도(애플리케이션/인프라)는 `docs/architecture/` 참고.

## 5. RAG 지식베이스 구축 방식

지식베이스 구축은 **미리 한 번 해두는 준비 작업**이다.

1. **문서 수집** — 전기 회사 민원 전반의 규정·FAQ·매뉴얼을 모은다. 경력인증 관련 자료(발급 절차·인정 기준·제출 서류 등)는 문의가 많은 만큼 비중 있게 갖춘다 (핵심 5~10개로 시작)
2. **청크 분리** — 문서를 300~500자 단위로, 약간 겹치게 쪼갠다
3. **임베딩** — 각 청크를 임베딩 API로 벡터(숫자)로 변환한다
4. **저장** — (청크 + 벡터 + 출처 메타데이터)를 ChromaDB에 저장한다

**주의사항**
- 저장할 때와 검색할 때 **같은 임베딩 모델**을 써야 한다.
- 청크 크기가 답변 품질을 좌우한다. 결과를 보며 조정한다.
- 청크마다 **출처 메타데이터**를 붙인다 (답변 근거 표시 + 평가 점수).

## 6. 문의 유형 (경력인증 반영)

| 유형 | 설명 | 예시 | 담당(예시) |
|---|---|---|---|
| 경력인증 | 경력증명 발급·인정 기준·수첩 관련 | "경력증명서 발급은 어디서 하나요?" | 경력관리팀 |
| 신청 | 서류·업무 처리 신규 요청 | "재직증명서를 신청하고 싶습니다." | 행정팀 |
| 변경 | 기존 신청·개인정보 변경 | "연락처를 변경하고 싶습니다." | 고객지원팀 |
| 취소/환불 | 신청 취소·환불 | "신청을 취소하고 싶습니다." | 고객지원팀 |
| 오류/장애 | 시스템 접속·기능 오류 | "로그인이 안 됩니다." | IT지원팀 |
| 일반문의 | 정책·일정·절차 안내 | "발급에 며칠 걸리나요?" | 민원안내팀 |
| 긴급문의 | 즉시 조치 필요 | "마감인데 처리가 안 됩니다." | 긴급대응팀 |

> 경력인증은 여러 문의 유형 중 하나로, 문의가 많아 추가·강조한다. 유형 표에 한 줄 넣는 것에서 끝나지 않고 RAG 지식베이스에 관련 자료 보강(2순위), 룰·부서 매핑 조정, 분류 프롬프트의 유형 목록 반영까지 함께 해야 실제로 동작한다. 나머지 일반 민원 유형도 동일하게 동작해야 한다.

## 7. 4주 일정

오늘 기준 약 4주. 매주 끝에 시연 가능한 상태를 유지한다.

### 1주차 — 뼈대: 텍스트 파이프라인
- 세팅: 레포·.gitignore·FastAPI 기본 구조 / NCP 콘솔에서 OCR·STT 사전 신청 병행
- 텍스트 문의 → 분류 → 룰 → RAG 검색 → 답변 초안까지 끝까지 연결
- 화면은 입력창 + 결과 표시 최소한
- **주말 상태**: 못생겼지만 텍스트로 끝까지 돌아가는 데모

### 2주차 — 도메인 + RAG 품질
- 전기 회사 민원 전반의 규정·FAQ·매뉴얼을 Vector DB에 채움 (경력인증 자료 비중 있게)
- 분류 유형·룰·프롬프트를 도메인에 맞게 조정 (경력인증 유형 추가 포함)
- 청크 크기 조정으로 답변 품질 향상
- **주말 상태**: 전기 회사 민원 데모로 그럴듯해진 상태 (경력인증 시나리오 포함)

### 3주차 — OCR·STT
- CLOVA OCR 먼저 (서류 이미지 → 텍스트)
- 되면 CLOVA Speech (음성 → 텍스트)
- 기존 파이프라인 앞에 얹기만, 뒤쪽 로직은 안 건드림
- **주말 상태**: 서류 사진 올리면 자동 입력되는 데모 (STT 막히면 OCR까지만)

### 4주차 — 마감
- UI 다듬기 (평가 UI/UX 항목)
- 산출물 문서 작성 (요구사항·화면설계·RAG/Rule 정의서 등)
- 발표자료·시연영상
- **개발은 3주차 끝에 동결**, 4주차는 다듬기·문서·발표에 집중
- **주말 상태**: 제출·발표 준비 완료

## 8. 평가 기준 대응

| 항목 | 배점 | 대응 |
|---|---|---|
| AI 활용성 | 30 | LLM 분류 + RAG + 프롬프트 설계 (1·2순위) |
| Rule 설계 | 15 | 키워드 룰 + LLM 분류 하이브리드, 우선순위·부서 기준 |
| 기능 완성도 | 20 | 문의 등록·분류·답변초안·부서추천 동작 (1순위) |
| UI/UX | 10 | 4주차에 다듬기 |
| 데이터 활용 | 10 | 전기 회사 민원 도메인 데이터 + AI HUB 평가셋 2종 |
| 발표/시연 | 15 | 아키텍처도 + 단계별 시연 시나리오 |

> 점수의 65%(AI 활용성·기능완성·룰)가 1·2순위에 집중. UI는 10점이므로 1주차에 화면 꾸미기에 시간을 쓰지 않는다.

### 데이터 활용 방침

데이터가 쓰이는 자리는 두 군데이며 성격이 다르다. 혼동하지 않는다.

- **RAG 지식베이스(답변 근거)** — 전기 회사 민원 FAQ·규정·매뉴얼을 직접 정리해 넣는다. AI HUB 데이터로 대체되지 않는다. (이게 답변 품질의 핵심)
- **평가용 데이터** — AI HUB 공개 데이터에서 2종을 사용한다. 시간 관계상 직접 수집은 생략.
  - 분류 평가용: 고객센터 상담 데이터 (환불·변경·오류·신청 등 유형이 우리 문의 유형과 부합)
  - RAG 답변 평가용: 문서 요약·질의응답 데이터 (문서·질문·정답·요약문 구조로 답변 적합도 측정)

> AI HUB 데이터는 "평가·참고용"이고, RAG에 실제로 들어가 근거가 되는 문서는 직접 정리한 전기 회사 민원 자료다. 자리가 다르다.

## 11. 결정 로그

진행하며 바뀐 결정은 여기에 날짜와 함께 기록한다.

- 초기 — 대상은 전기 회사 민원 전반. 경력인증은 문의가 많아 유형으로 추가·강조(주제는 아님). OCR/STT 추가(NCP 유료 API 사용). 배포 없이 로컬 구동. 백엔드는 FastAPI로 결정.
- 정정 — "도메인=경력인증"으로 좁게 적었던 표현을 "전기 회사 민원 시스템 + 경력인증 유형 추가"로 수정. 경력인증은 여러 유형 중 하나임을 명확히 함.
